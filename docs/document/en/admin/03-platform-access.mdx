Account roles control the management workspace. Credentials authenticate separate call paths. Select the role and credential that match the task.

<a id="admin-governance" />
## Separate business and platform roles

| Role | Main workspace | Authority |
| --- | --- | --- |
| User, `user` | Guardrail design, Integration and Runtime observability | Creates and manages business Guardrails, Policies, Routers and Endpoints. Inspects runtime logs and captured content. |
| Administrator, `admin` | Platform configuration and Access & audit | Configures shared models, capability bindings and accounts. Reads activity audits. Maintains platform Default operations. |

Administrators cannot mutate business resources or inspect tenant runtime logs. Business users cannot configure shared model services or read activity audits. Administrators retain read access to business metadata where management APIs permit it.

Roles apply across the shared workspace. They do not establish ownership isolation between business resources.

<a id="access-shared-operations" />
### Shared operational access

Both roles can inspect health, Runner status and software versions. They can adjust Runner capacity targets and remove registrations that the runtime permits. Serving instances remain protected. Personal-token writes require `runners:write`.

Users enter these pages through Settings. Administrators use the Platform operations sidebar. Both use the existing `/settings/*` paths.

Both roles retain account settings, password management, personal Access Tokens and documentation. Users inspect model usage through [Billing](/billing). Administrators manage model prices under [Models](/settings/models?tab=pricing).

Design workflows receive a reduced capability projection. It excludes Provider addresses, credential hints, control-plane model configuration and test bodies.

<a id="access-token-authority" />
### Personal-token authority

Effective authority is the intersection of the current account role and selected module grants. Write includes read. A role change recalculates existing token authority on subsequent requests.

A user can grant read access to runtime records and captured content. An administrator can grant audit access. Neither token can exceed its owning account's role. Router approval also requires an actor different from the submitter.

<a id="credential-types" />
## Select the credential for the call path

| Credential | Purpose | Boundary |
| --- | --- | --- |
| Browser session | Console operations with current account permissions. | Not a runtime inspection credential. |
| Personal Access Token | Automated management API calls within role, module and expiry limits. | Cannot issue other personal tokens. |
| Endpoint credential | Application or gateway inspection calls for one Endpoint. | Cannot sign in to the console or modify platform configuration. |
| Runner control credential | Controller–Runner control connection and configuration distribution. | Not for business inspection requests. |

<a id="platform-audit" />
## Review access and activity

Administrators assign roles under [accounts and access](/access). Each account manages its own [Access Tokens](/account/access-tokens).

Endpoint credentials appear in full only at issuance. Business users supply them to the associated application and rotate them as necessary.

Administrators review configuration activity in [Audit log](/audit-log). Users inspect request Decisions and findings in [Runtime logs](/logs). Health and rollout status remain separate from either record type.
