Runtime logs belong to the tenant (`user`) workflow. They include captured request and response bodies; platform activity audit records remain administrator-only.

Runtime logs answer “which protection handled this request, and what happened?” For example, if a support application reports that an ordinary order question was blocked, filter by Guardrail, time range, and Blocked outcome. Open the interaction to inspect the Guardrail Version, the input or output checkpoint, the matching Rule and the execution steps. The Router publication status tells whether the configuration was distributed. A runtime record shows what happened to one request.

<a id="runtime-log-views" />

## What the three views show

| View | Question it answers |
| --- | --- |
| **Interactions** | Was the protected request allowed, transformed, blocked, or failed overall? |
| **Guardrail checkpoints** | Which input or output check produced that result? |
| **System events** | What content-free metadata did the Runner report, such as Router, decision, and latency? Request and response bodies are not shown here. |

The page filters by Guardrail, time range, direction, and outcome. Entering from Router Monitoring can also supply Route, Target, and revision filters. This page has no separate Endpoint filter. To find the calls of one caller, compare request IDs, the routing context and the records of the integrating client.

<a id="term-evidence" />

## Evidence: execution evidence

Evidence is the set of findings, matching Policy and Rule, execution steps and version information that an inspection leaves to explain its Decision. Start with the outcome and matching Rule, then inspect the pinned version, Runner, errors, and latency. One Blocked record does not mean the entire Guardrail is unhealthy.

<a id="runtime-log-capture" />

## Enforce mode: how Rule risk and Log Level work together

Logging is configured per **Guardrail**, defaults to **INFO**, and applies across its versions. Users use **Guardrail → Actions → Edit log level** and save; DEBUG and TRACE require acknowledgement of content-capture costs. Once distributed to the Runner, the setting applies to new calls without republishing a version. A correlated call keeps the level selected at its first check. Raising the level does not recover historical bodies.

**Every level retains existing runtime records, findings, actions, versions, and execution traces.** Body capture depends on the logging level and the highest risk of a Rule actually matched anywhere in the call. Allowed traffic still has runtime records, but does not create a security finding by itself.

| Records in Enforce mode | INFO (default) | DEBUG | TRACE |
| --- | --- | --- | --- |
| Runtime records, correlation IDs, and versions for every check | Retained | Retained | Retained |
| Rule matches, risk severity, actual Action, and execution trace | Retained | Retained | Retained |
| Original request / response bodies for the whole call | Not retained | Retained when either phase matches a Medium, High, or Critical Rule | Retained for every call; no match required |
| Rewritten or transformed body copies | Not additionally retained | Not additionally retained | Not additionally retained |

<a id="concept-event-log-levels" />

### Body capture by matched Rule risk

| Highest matched Rule risk in the correlated call | INFO | DEBUG | TRACE |
| --- | --- | --- | --- |
| Critical | Runtime records and trace only | Runtime records, trace, and original bodies | Runtime records, trace, and original bodies |
| High | Runtime records and trace only | Runtime records, trace, and original bodies | Runtime records, trace, and original bodies |
| Medium | Runtime records and trace only | Runtime records, trace, and original bodies | Runtime records, trace, and original bodies |
| Low | Runtime records and trace only | Runtime records and trace only | Runtime records, trace, and original bodies |
| Informational | Runtime records and trace only | Runtime records and trace only | Runtime records, trace, and original bodies |
| No match, or no match with a known risk level | Runtime records and trace only | Runtime records and trace only | Runtime records, trace, and original bodies |

Only actual Rule matches select bodies. Non-matches, inconclusive results, and execution errors do not count as high-risk matches. **Action does not change this table**: a High Rule that only records and allows still selects bodies at DEBUG; a Low Rule that blocks or transforms neither becomes High nor selects bodies at DEBUG. INFO never retains bodies, including for blocks, timeouts, and fail-closed results. Error evidence remains available.

Rule `informational` describes risk; log INFO describes capture. Changing logging does not change protection mode, Rule risk, or enforcement actions.

<a id="runtime-log-request-response" />

## When both request and response are recorded

Capture uses the **whole correlated call**. The integration submits Input and Output under the same call ID: Input contains the incoming request and Output contains the model response. Different Runners may check the two directions.

- **INFO:** both directions retain runtime records and execution traces, without bodies.
- **DEBUG:** a Medium-or-higher match on either Input or Output selects the entire call, retaining the original input and output received. An output-only match also enriches the earlier input record with its original body.
- **TRACE:** retains original bodies from both directions whenever received, including completely allowed calls.

| One call in Enforce mode | Body retention |
| --- | --- |
| INFO: Input allows; Output matches High and blocks | Neither body; runtime records, findings, and traces remain |
| DEBUG: Input allows; Output matches High and blocks | Both correlated original bodies |
| DEBUG: Input matches Medium and allows; Output passes | Both correlated original bodies |
| DEBUG: only Low matches, even with a block or transformation | No bodies; runtime records, findings, and traces remain |
| TRACE: both Input and Output pass | Both original bodies |
| DEBUG with a High match, or TRACE: Input blocks and the caller does not invoke the model | Only the received Input body; no model response exists |

The integration must submit the content and reuse the call ID. For example, LiteLLM uses the same `litellm_call_id` for both directions. Missing Output, missing correlation IDs, or independent Scan calls cannot produce a missing counterpart. Scan's `requestPromptId` does not establish correlation.

<a id="runtime-log-content-boundary" />

### Scope of original content

Only **content received by the Runner** is retained. Rewritten request or response copies are not additionally stored. Existing Decisions, Actions, and execution traces still explain the handling performed.

Supported HTTP check endpoints retain the received HTTP body, method, target, and redacted request headers. Transport credentials such as authorization and cookies are excluded. An Output check's body contains the model response submitted by the integration; it is not the model provider's complete HTTP response envelope. Data never forwarded to Guardrail cannot appear in its logs.

Streaming output retains original text received during checks, correlated through the call's checkpoints. It excludes future text never received and is not a complete raw HTTP stream envelope. See [streaming output checks](/document/developer/gateway-connect#gateway-stream-protocol).

<a id="runtime-log-missing-content" />

### Why a log may have no body

Check the level at the call's first check, matched Rule risks, correlation ID, and whether the integration submitted the content. Users inspect captured bodies through Runtime observability → Runtime logs; platform administrators cannot access these tenant records. The separate system-events view does not display them.

DEBUG briefly holds candidate bodies while waiting for a later match. The correlation window is five minutes from the first check. Expiry, buffer capacity, or storage and delivery failures can leave incomplete content; existing runtime records are not deleted. Raising the level cannot recover expired or uncaptured bodies.

Monitor uses the risk of actual detected Rule matches too; its final allow does not cancel selection. Bypass performs no detection, so DEBUG cannot invent a risk match; TRACE can still retain received originals.

## Security events: separate risk, requested action, and execution outcome

Open **Guardrail → Security Events** to inspect detected issues. Select a time range in the toolbar, then open **Filters** to select one or more risk levels: Critical, High, Medium, Low, Informational, or Unclassified. The option counts cover the selected time range. The summary shows the matching events separately from the overall total. Remove the condition tag or choose **Clear filters** to restore all levels while keeping the time range. Filters are stored in the page URL and survive refresh or sharing. The risk level comes from the Rule version that the inspection used. Confidence and action do not change it. [Risk definitions and examples](/document/overview/glossary-definition#term-rule-risk-severity).

1. **Inspect risk and source:** identify the Policy, Rule, Endpoint, and evaluation phase.
2. **Inspect the requested action:** High · Record only means a high-risk detection was deliberately observed without intervention.
3. **Open the runtime log:** review whether the checkpoint allowed, transformed or blocked the traffic, and whether the inspection failed. The application or gateway must enforce `block` and `transform`. The log does not confirm that the downstream step completed.
4. **Inspect versions and confidence:** events retain the Policy Version, Guardrail Version, Rule risk, and requested action used at evaluation time. Missing confidence is shown as Not provided.

When several Rules match in one request, each match keeps its own level. The Router request summary shows the highest level. A safe result does not create a security event. A failed inspection stays in the runtime logs with a Check failed notice, independently of the final allow or block outcome. The risk level is not an investigation status. At this time there is no workflow to assign, close or suppress events.

<a id="concept-unclassified-events" />

### Why older records may be Unclassified

Older events and Guardrail artifacts may not contain a Rule risk snapshot. The system does not reconstruct history from current Policy settings or reuse the old confidence-derived rating. Test and publish a new Guardrail Version using classified Policies to include risk snapshots in subsequent events. Historical records remain unchanged.
