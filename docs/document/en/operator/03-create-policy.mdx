Policy Studio composes reusable Policies from registered detectors. Administrators can maintain shipped, locally created and imported Policies. Provenance belongs to compliance and traceability; it does not determine editing permission.

<a id="operator-policy-create" />

## Create and maintain

Choose **Create Policy** in the [Policy Library](/policy-library), or inspect a Policy and choose **Edit**.

The sidebar stepper follows **Basics → Rules → Test Cases → Review & publish**. You can revisit steps without losing edits; the footer keeps the next action visible.

1. Enter its name, purpose and Maintenance contact. This contact records responsibility; the administrator role grants write access.
2. Add at least one Rule. Choose a detector, input or output stages, handling action and detection parameters.
3. Text detectors cover keywords, regular expressions, conditions and fenced code. Ordinary rules require no Colang. The Detector selector also provides model classification, grounding and formal verification. Choose a classification profile and edit topic boundaries in the form; advanced JSON is reserved for complex conditions and parameter definitions.
4. Add a required acceptance Test Case for each Rule and each stage. Enter input text and the expected decision. Transform tests must assert the complete output text.
5. For model tests, expand **Test context** to supply trusted instructions. Grounding tests require the user query and reference sources. Formal verification requires a service policy ID, version, confidence threshold, user query and expected proof result. External detectors use the active binding in **Settings → Guardrail Catalog**; missing bindings and model errors fail the run.
6. **Save draft** adds a card to the Library immediately. An unpublished card displays Draft and cannot be bound to a Guardrail.

Renaming a Rule preserves its ID. Rules execute in order, passing transformed text forward; blocking ends evaluation. Deleting a Rule also removes draft tests that reference it.

<a id="operator-policy-declarative" />

## Definitions and detectors

The portable definition contains metadata, parameters, Rules, Test Cases and execution order. Each Rule references a versioned detector. The runtime supplies the implementation; origin and access permissions are outside this contract.

Keywords and regular expressions support replacement. Conditions and fenced-code detectors support detection and blocking. Model classification, grounding and formal verification require compatible capabilities in the target environment. Model credentials are not embedded in Policy definitions.

Parameterized Policies can declare test values in `testing.parameters` in the advanced definition. These values apply only to Studio tests; Guardrails use their own binding parameters. Phrase expansion creates an isolated test for each concrete entry. Test values cannot contain secrets.

**Export definition** downloads editable JSON. The Library import control loads this JSON as a new draft. Cross-environment Guardrail packages preserve referenced Policy identities, complete Rules and test definitions.

<a id="operator-policy-mechanism" />

## Executable tests

**Run tests** saves the draft and submits it to a healthy GuardRails 0 Runner. Compilation and evaluation use the same detectors as Guardrail execution.

- Rule acceptance cases run the selected Rule in isolation and require an actual match. A different Rule blocking first cannot count as acceptance.
- Clear the Rule acceptance checkbox to run a whole-Policy scenario, including safe inputs and ordering behavior.
- Replacement output is compared exactly. Runtime errors, unknown verdicts and missing results cannot serve as match evidence.
- Editing invalidates earlier results. An unavailable Runner produces an error instead of simulated publication evidence.

Some historical replacement cases specify only an expected decision. Add an exact expected output before testing and publishing changes to those Policies. Existing published versions remain unchanged.

<a id="operator-policy-release" />

## Publish and bind

In **Review & publish**, inspect each test’s decision, matched Rules and actual output. Use **Edit & run tests** to fix failures.

**Publish** becomes available after the current draft passes its required tests. The server verifies the draft revision and makes publication retries idempotent. Published versions are immutable.

Bind an exact Policy version in a Guardrail, then test and publish the Guardrail and configure routing. Maintaining a Policy creates a new draft; Guardrails pinned to earlier versions keep their behavior.

Guardrail export includes reachable Policy nodes. Pruning unused resources does not remove Rules from a referenced Policy or change that node's identity. Imported Policies remain maintainable by administrators. Legacy Colang Policies and signed historical versions retain compatibility readers and the existing editor.

<a id="operator-policy-risk-severity" />

## Risk and handling

Risk severity belongs to each Rule; handling determines the response to a match. New Rules default to medium severity. Advanced definitions allow changing severity and taxonomy. Guardrails may override handling, while severity changes require testing and publishing a new Policy version.

## Running the reference proof service

The repository includes an optional standalone Z3 service, independent of Controller and Runner state. Install it with `uv sync --extra formal --extra test`, set `FORMAL_SERVICE_API_KEY`, then run `.venv/bin/uvicorn runner.formal_service.app:create_app --factory --host 127.0.0.1 --port 8093`. The authenticated endpoint is `http://127.0.0.1:8093/evaluate`.

Register this endpoint as a custom Provider and a Model using `tali.automated-reasoning.v1`. In **Settings → Guardrail Catalog → Output**, select it for Automated Reasoning and validate `warranty-duration`, version `1`, with query `How long is the warranty?`, valid response `The warranty lasts one year.`, and invalid response `The warranty lasts ten years.` Save and apply the validated binding. Use the same policy reference in Studio, add a required invalid-proof Rule case plus a valid-proof scenario, run the tests, and publish.

The service proves bounded integer constraints. Its sample grammar accepts complete warranty sentences or JSON claims; it does not prove arbitrary natural-language answers. Unsupported text returns `no_translations`, inconsistent policies return `impossible`, and claims that are possible but not entailed return `satisfiable`. These are inconclusive for release. Low-confidence proof results also cannot establish a Rule match. Policy-specific tests remain required even after binding validation.

See `runner/formal_service/README.md` for the portable service policy format and proof semantics. Service policy definitions are a separately versioned external dependency; a Guardrail package carries the reference, not the external service's rule catalog.
