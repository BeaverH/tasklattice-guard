Policy Studio 用已有 Detector 组合可复用的 Policy。管理员可以维护平台提供、本地创建或导入的 Policy；来源只用于合规与追溯，不决定编辑权限。

<a id="operator-policy-create" />

## 创建和维护

在 [Policy Library](/policy-library) 选择 **创建 Policy**，或打开已有 Policy 后选择 **编辑**。

左侧步骤导航依次为 **基本信息 → Rules → Test Cases → 审查与发布**。切换步骤保留编辑内容，底部固定显示当前操作。

1. 填写名称、用途和 Maintenance 维护人。维护人用于记录责任，实际写权限由管理员角色控制。
2. 添加至少一条 Rule。选择 Detector、输入或输出阶段、命中动作，再填写检测参数。
3. 文本检测器包括关键词、正则表达式、组合条件和代码块检测。普通规则不需要编写 Colang。Detector 下拉框也提供模型分类、事实依据检查和形式验证；分类类型和话题边界可直接用表单编辑。复杂条件和参数定义保留高级 JSON 入口。
4. 每条 Rule 的每个阶段至少添加一个必选验收 Test Case，填写输入和预期动作。替换规则还必须断言完整的预期输出。
5. 模型用例可展开 **测试上下文** 填写可信指令；事实依据检查提供用户问题和参考资料。外部 Detector 使用 **设置 → Guardrail Catalog** 的已激活绑定，缺少绑定或模型调用异常会使测试失败。
6. **保存草稿** 后，Policy 立即出现在 Library 中。未发布的草稿显示 Draft，不能被 Guardrail 绑定。

Rule ID 在修改名称时保持不变。顺序决定执行行为，后续 Rule 读取前面的处理结果；阻断会结束本次检测。删除 Rule 会同时删除引用它的草稿测试。

<a id="operator-policy-declarative" />

## 声明式定义与 Detector

Policy 的声明式定义包含元数据、参数、Rules、Test Cases 和执行顺序。每条 Rule 引用有版本的 Detector；引擎实现由执行环境提供。平台来源和访问权限不属于这份可移植定义。

参数化 Policy 可以在高级定义的 `testing.parameters` 中设置测试值。测试值只用于 Studio 验收，Guardrail 使用自己绑定的参数。短语展开规则会按实际条目生成并隔离测试；这些测试值不能包含密钥。

关键词和正则支持替换。组合条件与代码块检测支持检测和阻断。模型分类、事实依据检查和形式验证需要目标环境具备对应能力；模型凭据不会放入 Policy 定义中。

**导出定义** 下载可编辑的 JSON。Library 的导入入口可以把它载入 Studio 作为新 Policy 草稿。完整 Guardrail 的跨环境迁移使用 Guardrail 资源包，保留引用的 Policy 版本、完整规则与测试定义。

<a id="operator-policy-mechanism" />

## 测试如何执行

点击 **运行测试** 会先保存当前草稿，再交给 GuardRails 0 的真实 Runner 编译和执行。测试使用与实际 Guardrail 相同的 Detector。

- Rule 验收用例隔离运行选中的 Rule，必须证明该 Rule 确实命中。另一条 Rule 提前阻断不能代替它通过验收。
- 取消“Rule 验收”后，用例作为整套 Policy 的场景测试，可以检查正常放行、规则组合和执行顺序。
- 替换结果按完整文本精确比较。运行错误、未知检测结果或缺少结果不能视为命中证据。
- 编辑后，之前的通过状态失效。没有健康 Runner 时，界面显示错误，不能以模拟结果发布。

部分历史替换用例只有预期动作，没有完整的预期输出。维护这些 Policy 时，需要先补全输出断言，再测试和发布；原有已发布版本继续保持不变。

<a id="operator-policy-release" />

## 发布与使用

在 **审查与发布** 中逐条查看测试动作、命中 Rule 和实际输出；通过 **编辑并运行测试** 返回修复失败。

当前草稿的必选测试通过后，才可以 **发布**。服务端检查测试对应的草稿版本，并发发布或重试不会创建重复版本。已发布版本不可变。

发布后，在 Guardrail 中绑定确切的 Policy 版本，再完成 Guardrail 自己的测试、发布和路由配置。维护已有 Policy 会产生新草稿；已绑定旧版本的 Guardrail 不会被自动修改。

Guardrail 导出携带被引用的 Policy 节点。裁剪未使用的资源不会删除这些 Policy 节点内的规则或改写它们的身份。导入后，管理员仍可维护新草稿。旧版 Colang Policy 和历史签名版本保留兼容读取及原有编辑入口。

<a id="operator-policy-risk-severity" />

## 风险与处理

风险级别属于 Rule，命中动作决定本次如何处理文本。新 Rule 默认使用中等风险；可在高级定义中修改风险级别和风险分类。Guardrail 可以覆盖处理动作，不能覆盖 Policy 的风险级别。调整风险后，应重新测试并发布 Policy 版本。


<a id="operator-policy-formal-service" />

## 启动参考证明服务

仓库提供可选的独立 Z3 服务，不依赖 Controller 或 Runner 状态。执行 `uv sync --extra formal --extra test`，设置 `FORMAL_SERVICE_API_KEY`，然后运行 `.venv/bin/uvicorn runner.formal_service.app:create_app --factory --host 127.0.0.1 --port 8093`。带认证的服务地址为 `http://127.0.0.1:8093/evaluate`。

将地址注册为自定义 Provider，Model 协议选择 `tali.automated-reasoning.v1`。在 **Settings → Guardrail Catalog → Output** 中选择该服务，验证策略 `warranty-duration` 的版本 `1`：问题填 `How long is the warranty?`，有效回答填 `The warranty lasts one year.`，无效回答填 `The warranty lasts ten years.`。通过后保存、应用绑定。

在 Studio 中选择形式验证 Detector，填写同一策略 ID、版本和证明置信度阈值。每个用例必须填写用户问题和预期证明结果；添加预期 `invalid` 的 Rule 验收，以及预期 `valid` 的放行场景。测试结果保留实际证明、命中 Rule 和调用次数，失败时不能发布。

该服务验证有限整数约束，支持完整的保修期句式或 JSON 断言，不验证任意自然语言。无法解析返回 `no_translations`，策略矛盾返回 `impossible`，仅可满足而无法证明返回 `satisfiable`，这些都不能作为放行证明；低于阈值的证明也不能作为 Rule 命中。绑定验证不替代 Policy 自己的测试。

服务策略格式见 `runner/formal_service/README.md`。服务中的形式规则是单独版本化的外部依赖；Guardrail 资源包携带其引用，不包含外部服务的规则目录。
