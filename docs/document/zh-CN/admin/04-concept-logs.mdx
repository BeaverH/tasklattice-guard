运行日志属于租户（`user`）使用功能，包含已采集的请求与响应正文；平台操作审计日志仅供管理员查看。

运行日志回答“请求实际经过了哪套保护，得到了什么结果”。例如，客服应用报告正常的订单问题被阻断：

1. 按 Guardrail、时间范围和“已阻断”筛选。
2. 打开对应的交互，核对 Guardrail Version、输入或输出检测点、命中的 Rule 和执行步骤。

Router 的发布状态说明配置是否已下发。运行记录才说明某次请求实际发生了什么。

<a id="runtime-log-views" />

## 三种视图各看什么

| 视图 | 用来回答的问题 |
| --- | --- |
| **交互** | 同一次受保护请求整体是放行、转换、阻断还是出错？ |
| **Guardrail 检查点** | 输入或输出阶段的哪次检查得到这个结果？ |
| **系统事件** | Runner 上报了什么运行元数据，例如 Router、决策和延迟？此视图不包含请求或响应正文。 |

页面提供 Guardrail、时间范围、方向和结果筛选。从 Router 的 Monitoring 进入时，还可以带入 Route、Target、revision 等路由条件。当前页面没有独立的 Endpoint 筛选器。排查某个调用方时，结合请求 ID、路由上下文和接入方的记录核对。

<a id="term-evidence" />

## Evidence：执行证据

这里的 Evidence 是本次检测留下的发现、命中的 Policy 和 Rule、执行步骤和版本等信息，用来解释 Decision。先看结果和命中的 Rule，再看固定的版本、Runner、错误或延迟。一条“已阻断”记录不代表整个 Guardrail 不健康。

<a id="runtime-log-capture" />

## Enforce 模式：Rule 等级与 Log Level 如何一起工作

日志等级按 **Guardrail** 设置，默认 **INFO**，对这个 Guardrail 的各个版本生效。用户在 **Guardrail → 操作 → 编辑日志等级** 中选择等级并保存；DEBUG、TRACE 需要确认正文采集成本。设置下发到 Runner 后用于新调用，无需重新发布版本。同一次关联调用沿用首次检查时的日志等级，提高等级不会补录历史正文。

**所有等级都保留已有运行记录、Rule 发现、处理结果、版本和执行 trace。** 正文是否保存，由日志等级与整次调用中实际命中的最高 Rule 风险级别共同决定。正常放行也保留运行记录，但不会因此生成安全事件。

| Enforce 模式下的记录内容 | INFO（默认） | DEBUG | TRACE |
| --- | --- | --- | --- |
| 每次检查的运行记录、关联 ID 与版本 | 保留 | 保留 | 保留 |
| Rule 命中、风险级别、实际 Action 与执行 trace | 保留 | 保留 | 保留 |
| 整次调用的原始 request / response 正文 | 不保存 | 任一阶段命中 Medium、High 或 Critical 时保存 | 全部保存，无需命中 Rule |
| 改写或转换后的正文副本 | 不另存 | 不另存 | 不另存 |

<a id="concept-event-log-levels" />

### 按命中的 Rule 风险级别查看正文采集

| 整次关联调用中命中的最高 Rule 等级 | INFO | DEBUG | TRACE |
| --- | --- | --- | --- |
| Critical / 严重 | 仅运行记录与 trace | 运行记录、trace 与原始正文 | 运行记录、trace 与原始正文 |
| High / 高 | 仅运行记录与 trace | 运行记录、trace 与原始正文 | 运行记录、trace 与原始正文 |
| Medium / 中 | 仅运行记录与 trace | 运行记录、trace 与原始正文 | 运行记录、trace 与原始正文 |
| Low / 低 | 仅运行记录与 trace | 仅运行记录与 trace | 运行记录、trace 与原始正文 |
| Informational / 信息 | 仅运行记录与 trace | 仅运行记录与 trace | 运行记录、trace 与原始正文 |
| 没有命中，或没有已知风险级别的命中 | 仅运行记录与 trace | 仅运行记录与 trace | 运行记录、trace 与原始正文 |

只有实际命中的 Rule 参与正文选择；未命中、结果不确定或执行错误不按高风险命中处理。**Action 不改变这个表格**：High Rule 即使仅记录并放行，在 DEBUG 下也会选择正文；Low Rule 即使阻断或转换，也不会自动升级为 High 或触发 DEBUG 正文采集。INFO 在阻断、超时、失败关闭时仍然不保存正文，错误和执行证据照常保留。

Rule 的 `informational` 描述风险，日志 INFO 描述采集策略，两者不是同一个等级。日志设置不改变保护模式、Rule 风险级别或处理指令。

<a id="runtime-log-request-response" />

## 什么情况下 request 和 response 都会记录

采集以**整次关联调用**为单位。接入方使用同一个调用 ID 提交 Input 与 Output：Input 是输入请求，Output 中包含模型响应。两个方向可以由不同 Runner 检查。

- **INFO**：两个方向都有运行记录与执行 trace，但都不保存正文。
- **DEBUG**：Input 或 Output 任一阶段命中 Medium 及以上 Rule，选择整次调用；保存已收到的输入原文与输出原文。出站才命中时，会补充此前入站检查的原始正文。
- **TRACE**：保存实际收到的两个方向原始正文，包括完全正常的调用。

| Enforce 模式下的一次调用 | 正文保留结果 |
| --- | --- |
| INFO：Input 放行，Output 命中 High 并阻断 | 两个方向均无正文；运行记录、命中与 trace 保留 |
| DEBUG：Input 放行，Output 命中 High 并阻断 | 保存关联 Input 和 Output 原文 |
| DEBUG：Input 命中 Medium 后放行，Output 正常通过 | 保存关联 Input 和 Output 原文 |
| DEBUG：只命中 Low，即使执行了阻断或转换 | 不保存正文；运行记录、命中与 trace 保留 |
| TRACE：Input、Output 都正常放行 | 两个方向原文都保存 |
| DEBUG 命中 High 或使用 TRACE：Input 被阻断，调用方不再调用模型 | 只有实际收到的 Input 原文；不存在模型 response |

关联要求接入方实际提交对应内容，并复用调用 ID。例如 LiteLLM 的两个方向使用相同的 `litellm_call_id`。没有提交 Output、缺少关联 ID，或只使用独立 Scan 时，系统无法补出另一个方向的内容；Scan 的 `requestPromptId` 不用于关联。

<a id="runtime-log-content-boundary" />

### 原始内容的范围

只保存 **Runner 实际收到的原文**，不额外保存改写后的 request 或 response。已有 Decision、Action 和执行 trace 仍能说明采取了什么处理。

支持的 HTTP 检查入口保留收到的原始 HTTP body，以及方法、目标和脱敏后的请求头；鉴权与 Cookie 等传输凭证不保留。Output 检查收到的 body 包含接入方提交的模型响应，它不等于模型服务完整的 HTTP 响应封装。没有转交给 Guardrail 的数据不会出现在日志中。

流式输出保留检查期间实际收到的原始文本，按同一调用的检查点关联；它不包含未收到的后续文本，也不是完整的原始 HTTP 流封装。见[流式输出检测](/document/developer/gateway-connect#gateway-stream-protocol)。

<a id="runtime-log-missing-content" />

### 为什么有日志却没有正文

先核对调用首次检查时的日志等级、命中的 Rule 等级、关联 ID 和接入方是否提交了内容。用户在「运行观测 → 运行日志」中按需展开已采集的正文，平台管理员不能访问这些租户记录。独立的系统事件视图不展示正文。

DEBUG 为等待后续命中短暂保留待选正文，关联窗口为首次检查起 5 分钟。关联超时、缓存容量不足或存储与上报异常可能导致正文不完整；已有运行记录不会因此被删除。提高日志等级不能恢复已经过期或未采集的内容。

Monitor 模式也按实际检测到的 Rule 风险选择正文，最终放行不会取消选择；Bypass 不执行检测，因此 DEBUG 不会凭空产生风险命中，TRACE 仍可保存收到的原文。

## 安全事件：风险、处理和执行结果分别看

在 **Guardrail → 安全事件** 查看检测发现的问题。在列表工具栏选择时间范围，点击“筛选”可同时勾选严重、高、中、低、信息，以及“未分级”。各选项右侧显示当前时段的数量。结果摘要分别显示匹配的事件数和时段总量。点击条件标签的 × 或“清除筛选”可恢复全部等级，时间范围保持不变。筛选条件保存在页面链接中，刷新或分享链接可恢复相同条件。风险级别来自当时使用的 Rule 版本。置信度和处理动作不会改变它。[风险级别的定义与例子](/document/overview/glossary-definition#term-rule-risk-severity)

建议按以下顺序调查：

1. **看风险和来源**：是哪条 Policy／Rule，在什么 Endpoint、哪个阶段产生了证据？
2. **看要求的处理**：是仅记录、遮盖还是阻断？“高风险 · 仅记录”表示规则发现了高风险问题，但当前配置选择观察。
3. **打开日志看实际结果**：检测点最终是放行、转换还是阻断？有没有超时或执行错误？接入方必须执行 `block` 和 `transform`。日志记录的是处理要求，不代表网关已经停止请求或使用了修改后的内容。
4. **看版本和置信度**：事件保留当时的 Policy Version、Guardrail Version、Rule 级别和处理指令。置信度未提供就显示“未提供”，不猜测一个分数。

同一次请求命中多条 Rule 时，每条证据单独分级。Router 的请求摘要取其中最高的级别。正常通过不生成安全事件。检测失败的记录保留在运行日志中，详情标记“检查异常”，最终是否阻断另行展示。安全事件的级别不表示人工调查进度。目前没有认领、关闭或抑制事件的工作流。

<a id="concept-unclassified-events" />

### 老版本为什么显示“未分级”

旧事件或旧 Guardrail 产物可能没有保存 Rule 级别。系统不会读取今天的 Policy 配置去猜测过去的风险，也不会把旧的置信度分级当作新级别。使用已定义风险级别的 Policy，测试并发布新的 Guardrail Version 后，新事件才会带上对应的级别。历史记录保留原样。
